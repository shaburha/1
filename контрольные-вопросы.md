# Ответы на контрольные вопросы

Лабораторная работа: серверное приложение на Node.js и Express.js.  
Предметная область: система совместного редактирования документов.  
Ресурс API: `/documents`.

## 1. Какие методы HTTP вы реализовали и для каких операций?

Реализованы четыре метода HTTP для CRUD-операций над документами:

| Метод | Маршрут | Операция |
| --- | --- | --- |
| `GET` | `/documents` | чтение списка документов |
| `GET` | `/documents/:id` | чтение одного документа |
| `POST` | `/documents` | создание документа |
| `PUT` | `/documents/:id` | полное обновление документа |
| `DELETE` | `/documents/:id` | удаление документа |

Дополнительно реализован служебный маршрут `GET /` с кратким описанием API.

## 2. Как получить параметры из URL (route params) и строку запроса (query string) в Express?

- **Route params** — именованные части пути, заданные как `:id`. Express кладёт их в объект `req.params`.  
  Пример: запрос `GET /documents/3` даёт `req.params.id === "3"`.

- **Query string** — параметры после `?`. Express кладёт их в объект `req.query`.  
  Пример: запрос `GET /documents?owner=ivanov&q=статья` даёт  
  `req.query.owner === "ivanov"` и `req.query.q === "статья"`.

В проекте `req.params.id` используется для поиска документа, а `owner` и `q` из `req.query` — для фильтрации списка.

## 3. Для чего используется middleware `express.json()`?

`app.use(express.json())` — встроенный middleware Express, который разбирает тело запроса с заголовком `Content-Type: application/json` и помещает результат в `req.body`.

Без него `req.body` будет `undefined`, и `POST`/`PUT` не смогут прочитать JSON-данные клиента. В проекте также подключён `express.urlencoded({ extended: true })` для данных формата `application/x-www-form-urlencoded`.

## 4. Какой HTTP-статус возвращается при успешном создании ресурса? При успешном удалении?

- Успешное создание (`POST /documents`): **201 Created**. Статус означает, что ресурс создан и в теле ответа возвращается новый документ с присвоенным `id`.
- Успешное удаление (`DELETE /documents/:id`): **204 No Content**. Статус означает, что операция выполнена, а тела ответа нет — удалять уже нечего возвращать.

## 5. Что такое REST API? Перечислите основные принципы REST.

**REST** (Representational State Transfer) — архитектурный стиль построения веб-API, в котором ресурсы идентифицируются URL, а операции над ними выражаются стандартными методами HTTP.

Основные принципы:

1. **Клиент-сервер** — клиент и сервер разделены и взаимодействуют только через API.
2. **Stateless** — каждый запрос содержит всю информацию, необходимую для его обработки; сервер не хранит состояние сессии клиента между запросами.
3. **Единообразный интерфейс** — ресурсы имеют стабильные URL, используются стандартные HTTP-методы и согласованные форматы представления (обычно JSON).
4. **Кэширование** — ответы могут помечаться как кэшируемые или нет.
5. **Многоуровневая система** — клиент не обязан знать, общается ли он напрямую с сервером или через прокси/шлюз.
6. **Код по требованию** (необязательный принцип) — сервер может передавать клиенту исполняемый код.

В данной работе API следует REST в упрощённом виде: ресурс `documents`, CRUD через HTTP, ответы в JSON.

## 6. Как организовать глобальную обработку ошибок в Express?

Глобальный обработчик — middleware с **четырьмя** аргументами: `(err, req, res, next)`. Он подключается **последним**, после всех маршрутов:

```js
app.use((err, req, res, next) => {
  const status = err.status || 500;
  res.status(status).json({ error: err.message });
});
```

В обработчиках маршрутов ошибка передаётся через `next(error)`. В проекте это сделано в `middleware/errorHandler.js`: функция `notFound` формирует 404 для неизвестных маршрутов, а `errorHandler` сериализует любую ошибку в JSON.

## 7. Какую структуру ответа сервера вы выбрали для ошибок?

Единый формат:

```json
{ "error": "Документ с id=99 не найден" }
```

Поле `error` содержит человекочитаемое сообщение. Для внутренних ошибок (статус 500) в режиме разработки дополнительно может возвращаться `stack`. Такой формат простой, одинаковый для 400/404/500 и удобен клиенту: достаточно читать одно поле.

## 8. Как протестировать DELETE-запрос, если ресурс уже был удалён? Какой статус должен быть возвращён?

Нужно повторно вызвать `DELETE /documents/:id` с тем же идентификатором. Первый запрос возвращает **204**, второй — **404** и JSON `{ "error": "Документ с id=... не найден" }`.

Это идемпотентность `DELETE` на уровне смысла операции «сделать так, чтобы ресурса не было»: повторное удаление не должно считаться успехом, если сервер честно сообщает, что объекта уже нет. В данной работе повторный DELETE трактуется как «ресурс не найден» и возвращает 404.

## 9. Какие преимущества даёт использование nodemon в процессе разработки?

`nodemon` следит за изменениями файлов и автоматически перезапускает Node.js-процесс. Преимущества:

- не нужно вручную останавливать и запускать сервер после каждой правки;
- быстрее цикл «изменил код → проверил API»;
- меньше риска тестировать старую версию кода.

В проекте он установлен как dev-зависимость и запускается командой `npm run dev`.

## 10. В чём разница между методами PUT и PATCH? Какой из них вы реализовали и почему?

- **PUT** заменяет ресурс целиком: клиент передаёт полное представление документа (`title`, `owner`, `content`, `collaborators`). Отсутствующие поля считаются сброшенными к значениям по умолчанию (например, пустой `content`).
- **PATCH** изменяет только переданные поля, остальные остаются без изменений.

Реализован **PUT**, потому что так требует задание лабораторной работы (полное обновление элемента). PATCH логично добавить позже, когда понадобится частичное редактирование (например, смена только заголовка или списка соавторов).

## 11. Как можно добавить поддержку CORS в ваше приложение? (Теоретически)

CORS (Cross-Origin Resource Sharing) разрешает браузеру обращаться к API с другого origin (например, React-клиент на `http://localhost:5173` и API на `http://localhost:3000`).

Практический способ:

```bash
npm install cors
```

```js
const cors = require('cors');
app.use(cors());
```

Для продакшена лучше явно указать origin фронтенда:

```js
app.use(cors({ origin: 'http://localhost:5173' }));
```

Альтернатива без пакета — вручную выставлять заголовки `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods` и обрабатывать preflight-запросы `OPTIONS`. В следующих работах CORS понадобится при интеграции с клиентом из 1 части курса.

## 12. Почему в данном задании данные хранятся в массиве, а не в базе данных? Когда стоит переходить на БД?

Массив в памяти выбран, чтобы сосредоточиться на маршрутизации, HTTP-методах, валидации и статусах, не отвлекаясь на СУБД. Данные живут только пока работает процесс сервера: после перезапуска коллекция возвращается к начальным значениям.

На базу данных стоит переходить, когда нужно:

- сохранять данные между перезапусками;
- работать с несколькими экземплярами сервера;
- искать, фильтровать и связывать большие объёмы данных;
- обеспечивать целостность, транзакции и одновременный доступ нескольких пользователей.

Для системы совместного редактирования документов БД понадобится уже в следующей лабораторной: документы, версии, пользователи и права доступа не должны теряться при остановке Node.js.

## 13. Какой заголовок Content-Type должен быть установлен для отправки JSON-данных?

```
Content-Type: application/json
```

Именно этот заголовок ожидает middleware `express.json()`. Если отправить JSON без него (или с `text/plain`), тело может не разобраться, и `req.body` останется пустым.

## 14. Напишите пример curl-команды для тестирования вашего POST-эндпоинта.

```bash
curl.exe -X POST http://localhost:3000/documents ^
  -H "Content-Type: application/json" ^
  -d "{\"title\":\"Новый документ\",\"content\":\"Текст\",\"owner\":\"ivanov\",\"collaborators\":[\"petrov\"]}"
```

В Unix/macOS достаточно одной строки:

```bash
curl -X POST http://localhost:3000/documents \
  -H "Content-Type: application/json" \
  -d '{"title":"Новый документ","content":"Текст","owner":"ivanov","collaborators":["petrov"]}'
```

Ожидаемый результат: статус **201** и JSON созданного документа с новым `id`.

## 15. Как убедиться, что сервер работает корректно после каждой модификации кода?

1. Запускать сервер через `npm run dev` — nodemon сам перезапустит процесс.
2. После перезапуска смотреть в консоль: должно появиться `Server running on http://localhost:3000`.
3. Повторять набор проверок: список, получение по id, создание, обновление, удаление, а также негативные случаи (400 и 404).
4. Использовать curl, REST Client VS Code или Postman. Минимальная проверка «сервер жив»: `GET http://localhost:3000/` или `GET http://localhost:3000/documents`.

Если после правки nodemon упал с ошибкой синтаксиса, запросы не выполнятся, пока ошибка не будет исправлена.

## 16. Какие шаги нужно предпринять, чтобы запустить ваше приложение на другом компьютере?

1. Установить [Node.js](https://nodejs.org/) (в поставку входит npm).
2. Скопировать проект или клонировать репозиторий (`git clone ...`, ветка `lab21`).
3. Перейти в папку проекта.
4. Выполнить `npm install` — установятся зависимости из `package.json` (`express` и `nodemon`). Каталог `node_modules` копировать не нужно.
5. Запустить сервер: `npm start` (обычный режим) или `npm run dev` (режим разработки).
6. Открыть `http://localhost:3000/` в браузере или отправить запросы на `http://localhost:3000/documents`.

Если порт 3000 занят, можно задать другой: `set PORT=4000` (Windows) и затем `npm start`.
